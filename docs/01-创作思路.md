# 创作思路

## 1. 一句话命题

用一只手的开合，控制一朵由 GPU 粒子构成的花。

这句话里只有三个变量：**手**、**开合**、**粒子**。整个项目所有设计决定，都是在这三个变量上做减法，而不是加法——不加音乐、不加场景切换、不加多花束、不加社交分享。

## 2. 为什么是两朵花

同一个交互骨架可以承载完全不同的视觉命题。与其做两个功能相似的页面，不如让两朵花走向对立面，用对照说明「骨架是通用的，花是个别的」。

| | 花信 | 莲境 |
| --- | --- | --- |
| 核心句 | 聚是一朵花，散是漫天星 | 八万粒子的一池莲花 |
| 变化维度 | 形态（花苞 → 花冠 → 星场） | 密度与光（开合、配色、位置） |
| 背景 | 暖近黑 `#130b0c` | 纯黑 `#030203` |
| 花瓣 | 四层圆瓣，5–7 瓣一层 | 四层尖瓣，12 / 10 / 8 / 6 瓣 |
| 附属结构 | 花茎、两片叶、花萼、星场 | 莲蓬、花丝、暖色芯光 |
| 粒子 | 13,000（4,000–30,000） | 80,000（20,000–120,000） |
| 手势的第二个作用 | 手掌位置带来轻微视差 | 手掌位置驱动整朵花平移 |

对照的价值在于：花信证明「一朵花可以散开」，莲境证明「一朵花可以不散开、只靠密度和光色成立」。两种做法共享同一套手势算法、同一套降级策略、同一种着色器写法。

## 3. 视觉语言

**共同约束**

- 只有黑色背景与发光粒子。亮度来自粒子 sprite 的柔和 alpha 与重叠，不使用后期 bloom——全屏辉光会掩盖花瓣层次，也会把作品推向霓虹感。
- 单朵花。不添加第二束花、飘落花瓣、地面倒影等装饰性元素。
- 不使用玻璃拟态、CSS 渐变、大面积阴影与圆角卡片。界面是扁平的、可读的、退到画面之后的。
- 字体只用系统字体：宋体承担标题与状态词，系统黑体承担操作与说明。不加载外部字体，不引入字体闪烁。
- 所有图形（花瓣、花苞、星场、莲花、界面中的线稿图标）均由程序化生成或内联 SVG 绘制，不使用外部图片与 3D 资产。

**分化**

- 花信是暖的：粉玫瑰、浅桃、暖白，花瓣边缘柔化，散开时铺成星野。
- 莲境是冷的：粉紫 / 蓝紫 / 暖金三套配色，同一组亮度级（深色基部 → 中间色 → 边缘高光），花瓣边缘连成薄光。

## 4. 交互哲学

**手势是增强，不是前提。** 页面在没有任何摄像头权限的情况下必须完整可用：滑块、画布拖动、键盘快捷键都能完成全部操作。摄像头被拒绝、设备不存在、非 HTTPS 上下文、模型加载失败——四条失败路径都回到手动模式，画布不中断。

**手动优先。** 用户一旦拖动滑块或点击形态，2.4 秒内手势不得抢回控制权。否则会出现「我只是想微调，手一动就被拽回去」的失控感。

**隐私前置。** 摄像头画面从不显示、不上传、不录制。取景框里只有 21 点骨架与静态手形提示。这既是隐私要求，也是视觉要求：真实影像会破坏纯黑画面。

**可以停下来。** `?still=1` 冻结动画，供截图与评审；`prefers-reduced-motion` 关闭入场与呼吸。一个用于展示的作品，必须能被安静地观看。

## 5. 技术命题

三个硬约束决定了实现形态：

1. **形态变化必须在 GPU 内完成。** 13,000 个粒子若逐帧在 CPU 上插值，主线程会被占满，手势延迟肉眼可见。因此每个粒子预存多套位置，顶点着色器按开合度插值，CPU 每帧只更新几个 uniform。
2. **一朵花只能有一个 draw call。** 花瓣、花心、花茎、叶片全部进同一个 `BufferGeometry`，用顶点属性区分类型，而不是多个 mesh。
3. **粒子数量必须可调。** 设备差异极大。数量控件实时重建几何并释放旧 GPU 缓冲，同时保留开合状态与配色——调密度不应该打断观看。

## 6. 明确的「不做」

- 不做多场景、不做页面滚动叙事、不做加载动画超过必要时长。
- 不做账号、不做数据上报、不做分享埋点。
- 不为移动端单独做一套简化版——同一套代码，用粒子数与像素比降级。
- 不用「粒子越多越好」当卖点：默认值是按中端设备调的，上限只是给愿意尝试的人。

## 7. 验收标准（项目级）

1. 握拳能辨认出完整的含苞形态；全开能辨认出花瓣层次，而不是一团发光点。
2. 任意中间开合值都是一帧完整画面，不是两段动画的过渡帧。
3. 摄像头不可用时，手动路径能完成全部操作且画面不降级。
4. 手机 390px 宽无横向溢出，键盘可完成主要操作。
5. 桌面 13,000 / 80,000 粒子下交互跟手，无持续掉帧。
6. 页面不请求任何非本源资源（离线可用），不加载外部字体与图片。
