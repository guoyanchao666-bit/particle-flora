# 版本管理与发布

本项目用「语义化版本 + 发布提交 + 变更日志」三件事记录演进。规则很轻，但必须一致，否则回看历史时会分不清哪次提交对应哪个可交付状态。

## 1. 版本号含义

采用 `MAJOR.MINOR.PATCH`：

| 位 | 何时递增 | 本项目示例 |
| --- | --- | --- |
| MAJOR | 交付形态发生断裂式变化：新增一个完整版本的花、入口结构重做 | 1.x → 2.0.0（新增莲境与入口页） |
| MINOR | 向后兼容的功能新增：新配色、新形态、新控件 | 2.0.0 → 2.1.0 |
| PATCH | 向后兼容的修复：着色器、降级路径、文档纠错 | 2.0.1 |

页面 URL 属于兼容性契约：`versions/<name>/` 一旦发布就不再改名，避免外部链接失效。

## 2. 提交信息约定

```
<type>(<scope>): <subject>
```

- `type`：`feat` 新功能 / `fix` 修复 / `docs` 文档 / `style` 视觉与格式 / `perf` 性能 / `chore` 工程杂项 / `release` 发布
- `scope`：`rose`、`lotus`、`portal`、`docs`、`ci`、`repo`
- 发布提交单独使用 `release: vX.Y.Z`，且**只包含版本号、CHANGELOG 与文档的改动**，不夹带功能。

示例：

```
feat(lotus): 新增暖金配色并同步界面强调色
fix(rose): 重建几何后保留当前开合
release: v2.0.0
```

## 3. 分支策略

单人项目，采用「主干 + 短分支」：

- `main` 始终可部署，任何提交都应能通过第 6 节的检查清单。
- 功能在 `feat/<name>` 上做，自测通过后合并回 `main`。
- 破坏性改动先在分支上同时改代码与文档，合并时一次进入 `main`。

## 4. 发布流程

1. **冻结范围。** 确认本次发布包含哪些提交，未完成的功能不进入本次版本。
2. **过检查清单。** 见 [创作指导 · 第 8 节](03-创作指导.md)。文档中的数字必须与代码一致。
3. **写 CHANGELOG。** 在 `CHANGELOG.md` 顶部新增条目，按「新增 / 变更 / 修复 / 文档 / 部署」分类，并写明兼容性影响。
4. **发布提交。** `git commit -m "release: v2.1.0"`，只含版本相关改动。
5. **打标签。** `git tag -a v2.1.0 -m "v2.1.0"` 并推送 `git push origin main --tags`。标签是版本的唯一权威标记，CHANGELOG 是它的说明。
6. **验证部署。** 推送后等待 Pages 构建完成，逐条打开入口页与各版本页，确认资源 200、控制台无报错。
7. **记录。** 如发布后发现问题，不回滚提交历史，而是发 `PATCH` 修复版本，并在 CHANGELOG 中标注。

## 5. 回滚

- **部署回滚**：在 Pages 设置中重新运行上一个成功版本的 workflow，或 revert 发布提交后推送。
- **代码回滚**：`git revert <release-commit>`，保留历史，不 `reset --hard`。
- **数据无状态**：项目无后端、无数据库、无用户数据，回滚不涉及迁移。

## 7. 本仓库的版本落地方式

本仓库的三个版本以**三个发布提交**落在 `main` 上，顺序即演进顺序：

1. `release: v1.0.0` —— 花信 + 基础工程 + 部署脚本（此时 `versions/lotus/`、`docs/`、`CHANGELOG.md` 尚不存在）。
2. `release: v2.0.0` —— 在其之上新增莲境、入口页、四篇文档与变更日志，并把 Pages 工作流从「单版本」改为「整站」。
3. `release: v2.1.0` —— 取消 `vendor/`、`models/` 的排除并入库，补开发日志，整理目录与文档口径。

查看版本之间的完整差异：

```bash
git log --oneline --decorate
git diff v1.0.0 v2.0.0 --stat
git diff v2.0.0 v2.1.0 --stat
```

> 标签可在有推送权限的环境中补打（`git tag -a v1.0.0 <sha>`）。若仓库由 API 通道初始化、未包含标签，可在 GitHub 的 **Releases → Draft a new release** 中基于对应提交创建同名标签，效果等价。

## 8. 文档随版本走

- `CHANGELOG.md`：面向使用者，说明每个版本变了什么。
- `docs/04-版本管理与发布.md`（本文）：面向维护者，说明怎么发版。
- 版本级 `README.md` / `creative/BRIEF.md`：描述该版本当前状态，随功能改动同步更新，不保留历史描述。
